## D01. 동시 요청 처리 모델

- **최종 선택** 메인은 수락한 연결의 읽기 가능 여부를 `poll()`로 감시하고 준비된 FD를 작업 큐에 넘긴다. 고정된 `pthread` 워커가 블로킹 I/O로 첫 `recv()`부터 처리한다.
- **선택 이유** 유휴 연결의 첫 요청을 기다리는 동안 워커를 다른 연결에 배정할 수 있으며 워커의 순차적인 수신·파싱·라우팅·응답 흐름이 유지된다. `poll()`은 macOS와 Linux에서 공통으로 사용한다. 감시 규모가 커지면 Linux `epoll`과 macOS `kqueue`를 검토한다. [README의 구현 방식](README.md#2-구현-방식)

**LMS 근거:** fork, pthread, I/O 멀티플렉싱 중 하나 이상으로 동시 요청을 처리해야 한다. pthread 방식은 스레드 풀을 권장한다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 수락 직후 워커 배정 | 연결 수락 후 바로 처리 가능 | 아무것도 보내지 않는 연결 4개가 워커 4개를 모두 점유 |
| 헤더 수신 후 워커 배정 | 헤더 수신 중 워커 사용 가능 | 메인이 연결별 헤더 버퍼와 수신 위치를 관리하고 헤더의 끝을 판별해야 함 |
| 연결마다 프로세스 생성 | 프로세스 사이에 메모리가 분리됨 | 생성 비용과 프로세스 관리가 필요하고, 공유 상태 관리가 번거로움 |
| **선택 · `poll()` 감시 + 스레드 풀** | 첫 바이트를 기다리는 동안 워커 사용 가능, 이후 순차적 처리 | `poll()`에 전달하는 목록 크기에 따라 감시 비용 증가, 일부만 수신한 요청과 Keep-Alive는 워커를 점유 |
| 논블로킹 I/O + 이벤트 루프 | 적은 스레드로 여러 연결의 준비된 I/O를 처리할 수 있음 | 연결별 수신·송신 진행 상태를 직접 관리해야 함 |

- **현재 구현:** `poll()`이 읽기 가능으로 반환하면 감시 목록에서 제거하고 FD를 포함한 연결 정보를 큐에 복사한다. 바이트는 워커가 `recv()`로 읽을 때까지 운영체제 수신 버퍼에 남는다. 읽기 가능 이벤트에는 EOF도 포함될 수 있으며 이 경우 워커가 연결을 정리한다. 큐의 mutex는 요청 처리 전에 해제한다.
- **검증:** 실제 TCP에서 워커 수와 같은 4개의 무응답 연결을 유지한 채 다섯 번째 GET이 완료되는지 확인한다. 첫 글자만 보낸 뒤 워커 큐 등록을 확인하고 나머지를 전송해 첫 바이트가 보존되는지도 검사한다.

## D02. 유지할 연결과 작업 큐의 상한

- **최종 선택** 첫 바이트를 기다리는 연결은 128개로 제한한다. 워커 4개를 고정하고 작업 큐는 64개로 제한한다. 작업 큐에 등록된 뒤 대기하는 시간에는 별도 상한을 두지 않는다.
- **선택 이유** 워커 수와 대기 소켓 수를 제한하면 부하가 커져도 서버가 사용할 자원을 예측할 수 있다. 고정 워커는 스레드 증감 로직이 필요 없고, 큐는 크기만 제한해 대기 정책을 단순하게 유지한다.

**LMS 근거:** 동시 처리, C10K 설계 고려사항, 메모리·자원 회수를 요구한다. 구체적인 연결 수나 상한 설정 방식은 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 별도 상한 없이 수락 | 애플리케이션의 명시적 제한 없이 접속을 받음 | 부하가 커지면 파일 디스크립터·메모리 등 OS 자원이 고갈될 수 있음 |
| **선택 · 연결 수와 작업 큐에 상한 설정** | 자원 사용량을 제한하고 부하 시 행동을 예측하기 쉬움 | 초과 접속 처리 정책이 필요함 |

워커 수 운영 방식도 비교했다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| **선택 · 고정된 수의 워커를 미리 생성해 재사용** | 스레드 생성·종료와 자원 사용량을 관리하기 쉬움 | 부하가 늘어도 워커가 자동으로 증가하지 않음 |
| 상한 내에서 워커 수를 자동 증감 | 부하에 맞춰 워커를 늘리고 한가할 때 자원을 줄일 수 있음 | 증감 조건과 워커 생성·종료 관리가 추가됨 |

- **적용 범위:** 첫 바이트 대기와 워커의 I/O에 D04의 타임아웃을 각각 적용한다.
- **감수할 비용:** 큐에 남은 연결 수는 제한하지만, 워커가 오래 점유되면 큐에 들어간 연결의 대기 시간은 길어질 수 있다.
- **현재 구현:** 감시 목록 128개, 작업 큐 64개, 활성 워커 4개, 수락 직후 인계·거절 중인 연결 1개까지 클라이언트 소켓은 최대 197개다. OS의 `listen()` 대기열은 별도로 관리된다.
- **조정:** 감시 상한은 `src/server.c`, 워커·작업 큐 상한은 `include/thread_pool.h`에서 관리한다.
- **검증:** 상한을 넘는 접속에서도 서버가 유지되고 연결·메모리가 계속 누적되지 않는지 확인한다.
- **검증 결과:** 실제 TCP에서 워커 4개와 대기 연결 64개를 채우고 추가 8개의 접속을 거절했다. 워커 하나가 비면 먼저 대기한 요청이 처리되는 것도 확인했다.

상한을 정할 때는 아래 항목을 구분한다.

```text
OS의 연결 수락 대기열     ← listen의 backlog
          ↓ accept
첫 바이트 감시 목록      ← 128개 / 최대 5초
          ↓ 읽기 가능
스레드 풀 작업 큐        ← 64개
          ↓ 워커 배정
워커가 처리 중인 연결    ← 워커 수
```

현재 `LISTEN_BACKLOG = 128`은 전체 연결 수 제한이 아니다.
애플리케이션이 유지하는 연결에는 감시·작업 대기·처리·인계 중인 연결이 포함된다.

## D03. 처리 용량 초과 시 행동

- **최종 선택** 첫 바이트 감시 목록이 가득 차면 새 연결을 닫는다. 작업 큐가 가득 차면 논블로킹으로 `503 Service Unavailable` 전송을 시도하고 초과 연결을 닫는다.
- **선택 이유** 접속을 담당하는 메인이 송신을 기다리지 않고 다음 접속을 받을 수 있다. 대기 연결이 더 쌓이는 것을 막는 대신, 초과 요청은 실패하고 클라이언트가 재시도할 수 있다.

**LMS 근거:** 동시 다중 접속과 부하 테스트에서의 동작을 검증해야 한다. 초과 요청을 어떻게 처리할지는 구현자의 선택이다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 큐가 비기를 기다리며 새 연결 수락을 늦춤 | 일시적인 부하를 대기로 흡수할 수 있음 | OS 대기열까지 차면 접속이 지연되거나 실패할 수 있음 |
| **선택 · 수락한 초과 연결을 빠르게 종료** | 대기와 자원 점유를 제한할 수 있음 | 클라이언트에 실패가 보이며 재시도가 발생할 수 있음 |

- **현재 구현:** 작업 큐가 찼을 때 `http_send_unavailable()`이 소켓을 논블로킹으로 바꾸고, 이미 도착한 데이터를 최대 16KiB 읽어 폐기한 뒤 `503` 응답을 시도한다. 읽지 않은 데이터로 인해 TCP reset이 응답을 끊을 가능성을 줄인다. 송신이 막히거나 실패해도 메인은 기다리지 않고 소켓을 닫는다.
- **관련 결정:** D02에 따라 고정된 워커 4개와 큐 64칸을 초기값으로 사용하고, 큐 대기 시간 제한은 우선 두지 않는다.
- **검증:** 실제 TCP에서 128개 연결 감시와 초과 연결 종료, 64개 작업 큐 포화와 `503` 응답을 각각 확인한다. 단위 테스트는 송신 버퍼가 가득 찬 상태의 논블로킹 실패도 검사한다. [부하 테스트 결과](README.md#부하-테스트-결과)

## D04. 아무것도 보내지 않거나 너무 천천히 보내는 연결

- **최종 선택** 연결 수락부터 첫 바이트 대기를 5초로 제한하고, 워커가 맡은 뒤 한 번의 수신·송신 대기는 30초로 제한한다. 요청 전체 수신 시간에는 상한을 두지 않는다.
- **선택 이유** 계속 데이터가 오는 느린 요청을 허용하면서 오래 응답이 없는 연결을 회수할 수 있다. 제한보다 짧은 간격으로 조금씩 보내는 연결은 더 오래 워커를 점유할 수 있다.
- **첫 바이트를 5초로 줄인 이유** 30초일 때는 아무것도 보내지 않는 연결 128개만으로 감시 목록을 채워 새 접속을 30초 동안 막을 수 있었다. 정상 클라이언트는 연결 직후 요청을 보내므로 첫 바이트 대기를 길게 둘 이유가 없다. Keep-Alive의 다음 요청 대기(D05)도 5초라서 "요청이 시작되기 전 대기는 5초"라는 하나의 규칙이 된다. 요청이 시작된 뒤에는 느린 네트워크와 큰 본문을 고려해 기존 30초를 유지한다.

**LMS 근거:** 연결 관리의 타임아웃, 비정상 클라이언트와 연결 종료 시 자원 회수를 고려해야 한다. 클라이언트 수신 제한 시간의 구체적인 값은 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 계속 기다림 | 느린 클라이언트를 오래 수용함 | 요청하지 않는 연결도 소켓과 워커를 점유함 |
| **선택 · 데이터가 오지 않는 시간 제한** | 아무것도 보내지 않는 연결을 회수할 수 있음 | 제한보다 느린 정상 클라이언트가 끊길 수 있고, 조금씩 계속 보내는 연결은 남을 수 있음 |
| 무응답 시간과 전체 수신 시간 모두 제한 | 조금씩 보내면서 자원을 오래 점유하는 연결도 제한함 | 큰 본문이나 느린 정상 요청을 허용할 범위까지 설계해야 함 |

- **현재 구현:** 메인은 수락 시 `CLOCK_MONOTONIC` 기준 만료 시각을 기록한다. 가장 이른 만료까지 `poll()`에서 기다리고, 읽기 가능 이벤트 없이 만료된 연결은 응답 없이 닫는다. 워커는 `SO_RCVTIMEO`와 `SO_SNDTIMEO`에 30초를 적용한다. 요청 수신 중 만료되면 `408` 응답을 시도하며, 송신 중 만료되면 연결을 닫는다.
- **검증:** 연결만 유지하는 클라이언트, 요청 중간에 멈추는 클라이언트, 제한 시간보다 짧은 간격으로 1바이트씩 보내는 클라이언트로 확인한다.
- **검증 결과:** 실제 TCP에서 아무것도 보내지 않는 연결이 약 5초 뒤 닫히고, 같은 시각에 연 연결이라도 5초 안에 요청을 보내면 `200`을 받는 것을 확인했다. 테스트용 짧은 타임아웃으로 헤더·본문 무응답을 확인했다. 전체 수신 시간이 무응답 제한보다 길어도 데이터가 계속 도착하면 수신에 성공하는 것을 검증했다.

## D05. Keep-Alive 연결의 재사용과 제한

- **최종 선택** 응답 경계를 알 수 있을 때 클라이언트 연결을 재사용한다. 다음 요청이 시작되지 않으면 5초 뒤 닫고, 요청이 계속 오면 100번째 응답을 완료한 뒤 닫는다.
- **선택 이유** 연속 요청의 연결 생성 비용을 줄일 수 있다. 워커가 4개이므로 유휴 상태의 대기는 5초로 제한하고, 유휴 제한에 걸리지 않는 연결도 100번째 응답 뒤 워커를 반환하게 했다. 상한에 도달하면 클라이언트가 새로 접속해야 한다.

**LMS 근거:** Connection 헤더와 Keep-Alive의 의미·처리를 이해하고 연결 수명을 관리해야 한다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 응답 하나마다 연결 종료 | 수명과 자원 관리가 단순함 | 다음 요청마다 새 연결이 필요함 |
| **선택 · 같은 연결에서 여러 요청 처리** | 연결 생성 비용을 줄일 수 있음 | 다음 요청의 바이트 보존과 유휴 연결 관리가 필요하며, 스레드 풀에서는 워커를 오래 점유할 수 있음 |

- **적용 범위:** 다음 요청을 기다리는 5초와 D04의 요청 수신 중 무응답 제한 30초는 구분한다. 연결 전체의 수명을 5초로 제한하는 정책은 아니다.
- **현재 구현:** 같은 워커가 연결별 reader를 유지하며 다음 요청을 처리한다. 요청별 본문·헤더 메모리는 응답 후 해제한다. HTTP/1.1의 기본 재사용과 명시적 close, 정적 응답의 HTTP/1.0 opt-in을 처리한다.
- **응답 경계:** Content-Length가 있는 응답과 본문 없는 204/304는 재사용한다. 길이 미지정·chunked 해제 후 전달하는 프록시 응답과 서버가 생성한 오류 응답은 close로 끝낸다. 백엔드 소켓은 요청마다 새로 연결한다.
- **유휴 회수:** 응답 후 다음 요청 시작만 최대 5초 기다린다. 만료 시 408을 덧붙이지 않고 닫는다. 다음 요청의 바이트가 이미 reader에 있거나 새로 도착하면 기존 30초 I/O 무응답 정책으로 수신한다. shutdown으로 유휴 대기도 즉시 깨운다.
- **요청 횟수 구현:** 연결별 카운터를 두고 100번째 요청을 라우팅하기 전에 재사용을 해제한다. 100번째 응답은 정상 전송하고 close로 끝낸다. reader에 남아 있는 추가 요청은 처리하지 않으며 새 연결에서 카운터를 초기화한다. 이 값은 include/http.h에서 관리하고 LMS가 지정한 값은 아니다.
- **검증:** 같은 연결의 연속 요청, 다음 요청을 보내지 않는 연결, 여러 연결이 Keep-Alive로 대기할 때 새 요청의 처리, 100번째 응답 후 종료와 새 연결의 카운터 초기화를 확인한다.
- **검증 결과:** 정적 파일·바이너리 POST 40회, 파이프라인의 본문 경계·응답 순서·close 이후 요청 차단, HTTP/1.0 opt-in, 잘못된 다음 요청, 유휴 워커 4개의 5초 회수와 큐 재개·즉시 종료를 실제 TCP로 확인했다. 시작한 다음 요청에는 기존 30초 정책이 적용되고, 프록시 응답 경계에 따라 재사용 또는 종료하는 것도 검증했다. 100번째 응답 정상 완료 후 종료·버퍼의 101번째 요청 차단·새 연결의 카운터 초기화를 확인했고, ASan·UBSan 단위/전체 TCP 통합 검사를 통과했다.

## D06. 종료 시 진행 중인 연결 처리

- **최종 선택** `SIGINT`·`SIGTERM`을 받으면 새 접속을 중단하고 큐의 연결과 처리 중인 연결을 끊은 뒤 자원을 정리한다.
- **선택 이유** 느린 클라이언트나 백엔드가 멈춰 있어도 종료 명령에 신속히 반응할 수 있다. 진행 중인 응답이 끊길 수 있으며, 워커가 소유한 소켓·파일·메모리는 회수한다.

**LMS 근거:** SIGINT·SIGTERM의 안전한 셧다운과 자원 회수를 요구한다. 진행 중인 요청을 얼마 동안 기다릴지는 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| **선택 · 모든 연결 즉시 종료** | 종료 시간이 짧음 | 진행 중인 요청과 응답이 끊김 |
| 모든 작업이 끝날 때까지 대기 | 진행 중인 요청을 완료할 기회를 줌 | 느리거나 멈춘 연결 때문에 종료가 지연될 수 있음 |
| 제한 시간 동안 기다린 뒤 종료 | 요청 완료 기회를 주면서 종료 시간을 제한함 | 대기 중인 작업과 처리 중인 연결을 추적해야 함 |

- **자원 정리:** 소켓 I/O 대기를 깨우고, 큐와 워커가 소유한 연결·파일·요청 메모리를 안전하게 정리하며 워커를 종료·회수한다. 즉시 종료는 요청 완료를 기다리지 않는 정책이며, 자원 정리 절차는 수행한다.
- **현재 구현:** 워커는 SIGINT·SIGTERM을 차단하고 메인이 종료 신호를 처리한다. 핸들러는 종료 표시와 논블로킹 파이프 알림만 수행한다. 메인은 새 접속을 중단하고 첫 바이트 감시 목록의 소켓을 닫는다. 스레드 풀은 큐를 비우고, mutex로 보호된 활성 소켓에 `shutdown()`을 호출해 I/O 대기를 깨운다. 각 워커는 요청·파일을 정리하고 자신의 소켓을 닫으며, 메인이 모든 워커를 join한 뒤 공유 문서 루트를 닫는다.
- **검증:** 요청 처리 중 SIGINT·SIGTERM을 보내 종료 시간, 클라이언트 결과, 워커와 소켓 정리를 확인한다.
- **검증 결과:** 빈 큐·수신 중·느린 수신자에게 송신 중·큐 포화 상태의 종료와 같은 포트 재실행을 확인했다. ASan·UBSan으로 전체 TCP 통합 테스트와 스레드 풀 단위 테스트를 통과했다. 요청 완료를 기다리는 유예 시간은 두지 않는다.

## D07. POST 본문 보관 방식

- **최종 선택** 요청 본문은 최대 1MiB까지 전부 받은 뒤 처리하고, 요청이 끝나면 저장 공간을 해제한다.
- **선택 이유** 본문 길이를 확인한 뒤 할당하므로 요청마다 사용하는 본문 메모리에 상한을 둘 수 있다. 완성된 본문을 라우터와 프록시에 넘기면 수신 도중의 실패 처리도 한곳에서 관리할 수 있다.

**LMS 근거:** POST 본문 처리, 매우 큰 본문에 대한 대응, 버퍼와 메모리 관리를 요구한다. 본문을 모아서 처리할지 스트리밍할지는 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| **선택 · 본문 전체 수신 후 처리** | 파싱·라우팅·프록시로 전달하는 흐름이 단순함 | 동시 요청 수와 본문 크기에 비례해 메모리를 사용함 |
| 받으면서 처리·전달 | 큰 본문을 제한된 버퍼로 처리할 수 있음 | 수신·처리를 연결하고 중간 실패를 처리하는 로직이 복잡해짐 |

- **메모리 할당:** Content-Length의 형식과 범위를 확인하고, 본문 상한 이내인지 검증한 다음 할당한다.
- **적용 범위:** 클라이언트 요청 본문을 전부 받은 뒤 처리한다는 결정이다. 응답 본문도 전부 메모리에 모아야 한다는 뜻은 아니다.
- **메모리 수명:** 요청마다 필요한 본문 저장 공간을 확보하고, 처리가 끝나거나 중간에 실패하면 해제한다. 계속 재사용하는 버퍼를 기본 크기로 축소하는 방식은 사용하지 않는다.
- **현재 구현:** 본문 크기 상한의 초기값은 1MiB다. 상한을 넘으면 메모리를 할당하기 전에 413으로 거절한다. 이 수치는 부하 테스트로 튜닝한 확정값은 아니다.
- **구현 단계:** HTTP 수신·파싱에 적용했다. 헤더는 최대 16KiB, URI는 최대 2KiB, 헤더 개수는 최대 100개로 제한하는 초기값을 사용한다.
- **검증:** 본문 분할 수신, 상한 경계와 초과, 수신 도중 연결 종료 시 메모리 회수를 확인한다.
- **검증 결과:** 11바이트 분할 본문, NUL이 포함된 본문, 1MiB 본문의 실제 TCP 수신, 길이가 부족한 본문의 EOF·무응답 처리를 확인했다. AddressSanitizer·UndefinedBehaviorSanitizer 테스트도 통과했다.

## D08. 요청 본문 길이 결정 방식의 지원 범위

- **최종 선택** `Content-Length`로 요청 본문의 경계를 판별한다. POST에서 헤더가 없으면 `411`로 응답하며, 빈 본문은 `Content-Length: 0`으로 표시한다.
- **선택 이유** LMS가 요구한 길이 기반 수신으로 본문 끝을 명확하게 판별할 수 있다. 지원 범위가 분명하도록 chunked 요청이나 길이 정보가 충돌하는 요청은 오류로 처리한다.

**LMS 근거:** Content-Length 기반 본문 길이 처리를 명시한다. chunked 요청 본문 수신은 필수 최소 범위로 명시하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| **선택 · Content-Length 기반부터 지원** | LMS의 최소 구현 범위에 집중할 수 있음 | 지원하지 않는 전송 방식은 명확히 거절해야 함 |
| chunked 요청 본문까지 지원 | 더 다양한 클라이언트 요청을 처리함 | 조각별 길이와 종료 경계의 파싱·검증이 추가됨 |

- **본문 없는 요청:** 일반 GET처럼 Content-Length와 Transfer-Encoding이 모두 없는 요청은 본문 길이 0으로 처리한다. 모든 요청에 Content-Length를 요구하는 정책은 아니다.
- **필수 처리:** 지원하지 않는 Transfer-Encoding을 무시하거나 Content-Length로 대신 해석하지 않고 거절한다.
- **현재 구현:** GET·POST와 HTTP/1.0·1.1 요청 라인, 헤더, 본문 길이를 해석한다. HTTP/1.1의 Host 누락·중복, Content-Length의 잘못된 형식·중복·범위 초과를 거절한다.
- **현재 구현:** Transfer-Encoding만 있으면 501, Content-Length와 함께 있으면 400으로 거절한다. 아직 지원하지 않는 Expect 요청은 417로 거절해 본문을 기다리는 상태에 빠지지 않게 한다.
- **구현 단계:** HTTP 수신·파싱에 적용했다. 백엔드 응답 중계 방식은 이 결정과 별도로 정한다.
- **검증 결과:** 정상·잘못된 Content-Length, 길이 없는 POST의 411 응답, 길이 0인 POST와 길이 헤더 없는 GET의 허용, 지원하지 않는 전송 방식과 서로 충돌하는 길이 정보의 거절을 단위·TCP 통합 테스트로 확인했다.

## D09. 정적 파일 제공 주체와 문서 루트 경계

- **최종 선택** C 서버가 문서 루트 아래의 일반 파일을 직접 제공한다.
- **선택 이유** 파일 접근 범위와 MIME, 오류 응답을 C 서버 한 곳에서 제어하고 테스트할 수 있다. 대신 파일 열기와 경로 검사를 서버가 직접 맡는다.

**LMS 근거:** 문서 루트의 파일 제공, MIME과 기본 오류 응답이 필수다. Reverse Proxy 항목에서는 정적 요청을 직접 처리할지 애플리케이션 서버로 전달할지 선택할 수 있다.

- **기본 구현 정책:** 문서 루트 디렉터리를 열어 유지하고 `openat()`으로 구성요소마다 접근한다. `..`와 심볼릭 링크를 거절하고 일반 파일만 제공한다. 디렉터리 목록은 제공하지 않는다.
- **현재 구현:** 정상 파일은 200, 없음은 404, 권한·금지된 경로는 403, 예상하지 못한 파일 오류는 500으로 응답한다.
- **검증:** 직접·인코딩된 경로 우회, 루트 안/밖을 가리키는 링크, 디렉터리 링크, FIFO와 권한 거절을 확인했다. 500 응답은 유효하지 않은 루트 디스크립터를 주입한 모듈 테스트로 확인했다.

## D10. 정적 파일 전송 방식

- **최종 선택** 파일을 16KiB씩 `read()`로 읽고 `send()`로 전송한다.
- **선택 이유** 파일 크기와 관계없이 고정 크기 버퍼를 사용할 수 있고, macOS와 Linux의 공통 POSIX API로 작성할 수 있다. 짧게 송신된 경우의 나머지 전송과 파일 읽기 오류는 서버가 처리한다.

**LMS 근거:** 파일 내용을 HTTP 응답 본문으로 전송해야 하며 메모리·자원 관리와 macOS/Linux 이식성을 고려한다. read/send 사용을 직접 지정하지는 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 전체 파일을 읽은 뒤 전송 | 흐름이 단순함 | 파일 크기와 동시 요청 수만큼 메모리 사용 증가 |
| **선택 · read/send 반복** | 일정 크기의 작업 공간으로 큰 파일 전송 가능, 공통 API 사용 | 읽기와 송신의 진행·오류를 관리해야 함 |
| sendfile | 사용자 공간으로의 데이터 복사를 줄일 수 있음 | POSIX 표준 함수가 아니며 OS별 호출 방식 차이와 LMS의 표준 범위를 고려해야 함 |

- **현재 구현:** 16KiB 작업 공간을 반복 사용한다. `fstat()`으로 얻은 파일 크기를 Content-Length로 쓰고 읽은 바이트를 전부 송신한 뒤 다음 블록을 읽는다.
- **오류 처리:** 첫 읽기 실패는 200 전송 전에 500으로 처리한다. 응답 시작 후 파일이 줄거나 송신이 실패하면 연결을 닫는다. 이미 보낸 응답에 500을 덧붙이지 않는다.
- **검증:** 빈 파일, NUL이 포함된 다중 블록 바이너리, 실제 TCP의 4MiB 파일과 수신 중 클라이언트 종료를 확인했다.

## D11. 정적 요청과 API 요청의 경로 분리

- **최종 선택** 경로 접두사로 요청을 분류한다. 기본값은 `/api`이며 정확히 `/api`인 요청과 `/api/` 아래 요청을 백엔드로 보낸다.
- **선택 이유** 별도 호스트 설정 없이 한 서버에서 정적 파일과 API를 제공하고, 주소만 봐도 처리 경로를 알 수 있다. 이 접두사 아래는 API 영역으로 사용한다.

**LMS 근거:** Reverse Proxy는 경로나 Host 기반으로 라우팅할 수 있다.

- **현재 구현:** `/`와 `/docs/`는 `index.html`을 찾는다. 정적 파일은 GET만 허용하며 POST에는 405와 `Allow: GET`을 보낸다. API 영역은 설정된 백엔드로 중계하며 백엔드가 없으면 503으로 응답한다. --proxy-prefix로 접두사를 바꿀 수 있고 경로 구성요소 경계를 구분한다.
- **경로 처리:** 쿼리 분리 → 한 번의 퍼센트 디코딩 → 경로 검증·정규화 → 라우팅 순서다. 실제 프록시 전달 시 원래 요청 주소는 그대로 사용할 수 있도록 남겨 둔다.
- **검증:** 루트·중첩 index, 쿼리, 공백·한글 파일명, `/api`와 `/apix` 경계, 잘못된 인코딩과 상위 경로의 거절을 확인했다.

## D12. 백엔드 응답 본문 전달 방식

- **최종 선택** 백엔드 응답 헤더를 먼저 검증한 뒤, 본문은 16KiB 버퍼를 재사용해 스트리밍한다.
- **선택 이유** 응답 전체를 저장할 메모리가 필요하지 않고, 클라이언트가 첫 바이트를 더 일찍 받을 수 있다. 응답을 이미 보내기 시작한 뒤 중계가 실패하면 연결을 닫아 종료한다.

**LMS 근거:** 백엔드 응답 중계와 메모리 관리, 타임아웃·비정상 종료 처리를 요구한다. D07의 요청 본문 보관 정책과 별개로 응답 전달 방식을 정한다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 크기 상한 내에서 응답 전체를 모은 뒤 전송 | 수신 완료를 확인한 뒤 응답하거나 오류를 반환할 수 있음 | 큰 응답에서는 메모리를 많이 쓰며 전송 시작이 늦어짐 |
| **선택 · 응답 헤더 검증 후 본문을 조금씩 받아 전송** | 일정 크기의 작업 공간을 사용하고 본문 전달을 빨리 시작함 | 전송 시작 뒤 실패하면 새 502/504 응답으로 교체할 수 없어 연결을 종료해야 함 |

- **현재 구현:** 헤더를 최대 16KiB·100개까지 수신·검증하고 본문은 16KiB 버퍼를 반복 사용해 전송한다. Content-Length·연결 종료·chunked 응답을 처리한다. chunked는 내용을 해석해 조각 구분자를 제거하고 클라이언트 연결 종료로 본문 끝을 알린다. 응답 전체를 메모리에 쌓지 않는다.
- **HTTP 처리:** 홉별 헤더와 Connection이 지명한 필드는 제거하고 길이·Connection·Via 헤더를 재구성한다. 중복·충돌하는 길이 정보와 비정상 응답은 응답 시작 전 502로 거절한다. 백엔드의 4xx/5xx는 그대로 전달한다. 1xx는 최대 8개를 소비하고 101 Upgrade는 지원하지 않는다.
- **시간 제한·오류:** 연결 실패는 502, 연결·I/O 무응답 시간 초과는 응답을 시작하기 전 504다. 전체 요청 시간 상한은 추가하지 않는다. 선택한 백엔드에 요청을 자동 재전송하지 않는다. 백엔드 연결은 요청마다 새로 만들고 응답 처리 후 닫는다. 클라이언트 연결 재사용은 D05의 응답 경계와 유휴 정책에 따른다.
- **종료:** 워커가 백엔드 소켓을 풀에 등록한다. 메인이 종료 시 client/backend 양쪽 소켓을 shutdown하고, 워커가 등록 해제·close를 수행한다. 연결 성립 대기 중에는 최대 100ms 간격으로 종료 표시를 확인한다.
- **검증 결과:** 바이너리·1MiB POST, 4MiB 응답, 길이·종료·chunked·중간 1xx·본문 없는 응답, 잘못된 헤더·불완전 본문을 실제 TCP로 확인했다. 테스트 백엔드가 나머지 본문을 보내기 전 클라이언트에 첫 부분이 도착하는 것을 확인했다.

## D13. 백엔드 분산 방식

- **최종 선택** 실제 HTTP 백엔드 A·B에 API 요청을 Round-Robin으로 번갈아 보낸다.
- **선택 이유** 응답에 담긴 서버 식별자로 A → B 순서를 바로 확인할 수 있고, 한 백엔드의 실패를 재현할 수 있다. 각 요청의 분산 순서는 백엔드의 현재 부하와 무관하게 회전한다.

**LMS 근거:** Reverse Proxy의 여러 백엔드 라우팅을 구현하고, Round-Robin은 권장 사항으로 제시한다.

- **감수한 제약** 백엔드 응답 시간이 달라도 요청 수는 순서대로 분배한다. 응답이 멈춘 백엔드도 다음 순번에 다시 선택된다.
- **현재 구현:** 백엔드 배열의 다음 인덱스는 mutex로 보호하며, 정적 요청은 분산 순서를 소비하지 않는다. 백엔드가 실패해도 다음 요청은 다음 백엔드를 선택한다. 별도의 헬스 체크·자동 재시도·동적 백엔드 추가는 구현 범위에 포함하지 않는다.
- **검증 결과:** A/B 순차 분산과 40개 동시 요청의 20:20 분산을 확인했다. 백엔드 연결 거절의 502, 무응답 504, 백엔드 미설정 503, 60초로 설정한 백엔드 수신 대기 중에도 SIGTERM으로 즉시 정리되는 것을 확인했다. ASan·UBSan으로 단위·전체 TCP 통합 검사를 통과했다.
