# 설계 결정 기록

작성일: 2026-11-20
최종 갱신: 2026-11-23

사용자가 제공한 LMS 요구사항을 기준으로, 대안과 트레이드오프가 있는 결정을 기록한다.
연결 관리, 동시 처리, HTTP 요청 수신, 정적 파일 응답에 관한 결정을 정리한다.
일반적인 함수 사용법, 필수 오류 검사, 쉽게 바꾸는 포트 번호 등은 결정 항목에서 제외한다.

## 상태 구분

- **미정:** 사용자와 선택을 확정하지 않았다. 추천은 합의된 결정이 아니다.
- **잠정 방향:** 현재 구현 계획의 방향이다. 최종 확정과 구현 완료를 뜻하지 않는다.
- **확정:** 선택과 이유를 합의했다. 구현 여부는 별도로 기록한다.

## D01. 동시 요청 처리 모델

**LMS 근거:** fork, pthread, I/O 멀티플렉싱 중 하나 이상으로 동시 요청을 처리해야 한다. pthread 방식은 스레드 풀을 권장한다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 연결마다 프로세스 생성 | 프로세스 사이에 메모리가 분리됨 | 생성 비용과 프로세스 관리가 필요하고, 공유 상태 관리가 번거로움 |
| 블로킹 I/O + 스레드 풀 | 수신 → 처리 → 응답 흐름을 순차적으로 작성하기 쉬움 | 느린 연결이 워커를 점유하며, 공유 상태를 동기화해야 함 |
| 논블로킹 I/O + 이벤트 루프 | 적은 스레드로 여러 연결의 준비된 I/O를 처리할 수 있음 | 연결별 수신·송신 진행 상태를 직접 관리해야 함 |

- **확정:** 블로킹 I/O + 스레드 풀을 사용한다. 사용자는 워커 수를 고정하는 운영 방식을 선택했다.
- **선택 이유:** 기존의 수신 → 파싱 → 라우팅 → 응답 흐름을 워커에서 활용하고, 고정된 수의 워커를 재사용해 생성·종료 관리를 단순하게 유지한다.
- **현재 구현:** 메인은 accept한 연결 정보를 값으로 복사해 큐에 넣는다. 고정 워커 4개가 기존 handle_client의 HTTP 수신·파싱·라우팅·응답을 수행한다. 큐의 mutex는 요청 처리 전에 해제하며, 빈 큐에서는 condition variable로 대기한다.
- **결정 시점:** 스레드 풀 구현 전.
- **검증:** 한 클라이언트가 느릴 때 다른 요청이 처리되는지 확인한다.
- **검증 결과:** 실제 TCP에서 무응답 연결을 유지한 채 36개의 HTML·바이너리·POST 요청을 처리했다. 단위 테스트에서 48개 작업의 중복 없는 처리와 워커 재사용을 확인했고, 스레드 풀의 ThreadSanitizer 검사도 통과했다.

## D02. 유지할 연결과 작업 큐의 상한

**LMS 근거:** 동시 처리, C10K 설계 고려사항, 메모리·자원 회수를 요구한다. 구체적인 연결 수나 상한 설정 방식은 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 별도 상한 없이 수락 | 애플리케이션의 명시적 제한 없이 접속을 받음 | 부하가 커지면 파일 디스크립터·메모리 등 OS 자원이 고갈될 수 있음 |
| 연결 수와 작업 큐에 상한 설정 | 자원 사용량을 제한하고 부하 시 행동을 예측하기 쉬움 | 초과 접속 처리 정책이 필요함 |

워커 수 운영 방식도 함께 결정한다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 고정된 수의 워커를 미리 생성해 재사용 | 스레드 생성·종료와 자원 사용량을 관리하기 쉬움 | 부하가 늘어도 워커가 자동으로 증가하지 않음 |
| 상한 내에서 워커 수를 자동 증감 | 부하에 맞춰 워커를 늘리고 한가할 때 자원을 줄일 수 있음 | 증감 조건과 워커 생성·종료 관리가 추가됨 |

- **확정:** 워커 수를 고정한다. 서버 시작 시 정해진 수를 만들고 실행 중에는 자동 증감하지 않는다. 사용자가 고정형을 선택했다.
- **확정:** 작업 큐의 크기를 제한한다. 사용자는 우선 큐 크기만 제한하고 큐에서의 대기 시간 제한은 두지 않는 정책을 선택했다.
- **적용 범위:** 큐에서 기다리는 시간은 워커가 요청 처리를 시작한 뒤 적용하는 D04의 수신·송신 무응답 제한과 별개다. 큐 대기 시간 제한은 이후 안정화 단계에서 검토할 수 있다.
- **감수할 비용:** 큐에 남은 연결 수는 제한하지만, 워커가 오래 점유되면 큐에 들어간 연결의 대기 시간은 길어질 수 있다.
- **현재 구현:** 초기값은 워커 4개, 큐 64칸이다. 큐 크기는 처리 중인 연결을 제외한 대기 연결 수다. 접속 담당이 수락 직후 인계·거절 중인 연결 1개까지 클라이언트 소켓은 최대 69개다. OS의 listen 대기열은 이 수에 포함하지 않는다.
- **조정:** 초기 수치는 include/thread_pool.h에서 관리하며, 정식 부하 테스트로 튜닝한 값은 아니다. 실행 중에는 고정값을 유지한다.
- **결정 시점:** 스레드 풀과 작업 큐 구현 전.
- **검증:** 상한을 넘는 접속에서도 서버가 유지되고 연결·메모리가 계속 누적되지 않는지 확인한다.
- **검증 결과:** 실제 TCP에서 워커 4개와 대기 연결 64개를 채우고 추가 8개의 접속을 거절했다. 워커 하나가 비면 먼저 대기한 요청이 처리되는 것도 확인했다.

상한을 정할 때는 아래 항목을 구분한다.

```text
OS의 연결 수락 대기열     ← listen의 backlog
          ↓ accept
수락한 연결의 작업 대기열 ← 작업 큐 크기
          ↓
워커가 처리 중인 연결    ← 워커 수
```

현재 `LISTEN_BACKLOG = 128`은 전체 연결 수 제한이 아니다.
애플리케이션이 유지하는 연결에는 작업 대기 중인 연결, 처리 중인 연결, 수락 직후 인계 중인 연결도 포함한다.

## D03. 처리 용량 초과 시 행동

**LMS 근거:** 동시 다중 접속과 부하 테스트에서의 동작을 검증해야 한다. 초과 요청을 어떻게 처리할지는 구현자의 선택이다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 큐가 비기를 기다리며 새 연결 수락을 늦춤 | 일시적인 부하를 대기로 흡수할 수 있음 | OS 대기열까지 차면 접속이 지연되거나 실패할 수 있음 |
| 수락한 초과 연결을 빠르게 종료 | 대기와 자원 점유를 제한할 수 있음 | 클라이언트에 실패가 보이며 재시도가 발생할 수 있음 |

- **확정:** 작업 큐가 가득 차면 수락한 초과 연결을 빠르게 거절한다. 사용자가 빠른 거절을 선택했다.
- **응답 방침:** 가능하면 `503 Service Unavailable` 응답을 보내고 연결을 닫는다. 응답 전송 때문에 접속 담당 스레드가 오래 멈추지 않도록 하며, 전송할 수 없어도 연결을 정리한다.
- **선택 이유:** 이미 받은 작업에 집중하고 대기 연결과 자원 점유가 계속 누적되는 것을 막는다. 초과 접속은 실패하며 클라이언트의 재시도가 발생할 수 있음을 감수한다.
- **현재 구현:** 큐가 찼을 때 http_send_unavailable이 소켓을 논블로킹으로 바꾸고 503 응답을 시도한다. 송신이 막히거나 실패해도 메인은 기다리지 않고 소켓을 닫아 다음 접속을 받는다.
- **관련 결정:** D02에 따라 고정된 워커 4개와 큐 64칸을 초기값으로 사용하고, 큐 대기 시간 제한은 우선 두지 않는다.
- **결정 시점:** 스레드 풀에 작업을 넣는 로직 구현 전.
- **검증:** 큐를 가득 채운 상태에서 새 접속의 결과, 응답 지연, 자원 사용을 확인한다.
- **검증 결과:** 큐 포화 상태의 새 접속에서 503 응답과 연결 종료를 확인했다. 단위 테스트에서 송신 버퍼가 이미 가득 찬 경우에도 과부하 응답 전송이 블로킹하지 않는 것을 확인했다.

## D04. 아무것도 보내지 않거나 너무 천천히 보내는 연결

**LMS 근거:** 연결 관리의 타임아웃, 비정상 클라이언트와 연결 종료 시 자원 회수를 고려해야 한다. 클라이언트 수신 제한 시간의 구체적인 값은 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 계속 기다림 | 느린 클라이언트를 오래 수용함 | 요청하지 않는 연결도 소켓과 워커를 점유함 |
| 데이터가 오지 않는 시간 제한 | 아무것도 보내지 않는 연결을 회수할 수 있음 | 제한보다 느린 정상 클라이언트가 끊길 수 있고, 조금씩 계속 보내는 연결은 남을 수 있음 |
| 무응답 시간과 전체 수신 시간 모두 제한 | 조금씩 보내면서 자원을 오래 점유하는 연결도 제한함 | 큰 본문이나 느린 정상 요청을 허용할 범위까지 설계해야 함 |

- **확정:** 데이터를 받지 못하고 기다리는 시간만 제한한다. 요청 전체를 받는 데 걸리는 시간의 상한은 이번 구현에 추가하지 않는다.
- **선택 이유:** 사용자 선택에 따라 데이터가 계속 도착하는 느린 요청은 허용하고, 무응답 연결을 정리한다.
- **감수할 비용:** 제한 시간보다 짧은 간격으로 조금씩 전송하는 연결은 오래 유지될 수 있다.
- **현재 구현:** 무응답 제한 시간의 초기값은 30초다. 초과하면 408 응답을 시도하고 연결을 정리한다. 이 수치는 부하 테스트로 튜닝한 확정값은 아니다.
- **구현 참고:** 블로킹 수신의 소켓 타임아웃을 활용할 수 있다. 전체 수신 시간 측정을 제외하는 이유를 시간 조회 비용이 크기 때문이라고 해석하지 않는다.
- **결정 시점:** 블로킹 요청 수신 반복문 구현 전.
- **검증:** 연결만 유지하는 클라이언트, 요청 중간에 멈추는 클라이언트, 제한 시간보다 짧은 간격으로 1바이트씩 보내는 클라이언트로 확인한다.
- **검증 결과:** 테스트용 짧은 타임아웃으로 헤더·본문 무응답을 확인했다. 전체 수신 시간이 무응답 제한보다 길어도 데이터가 계속 도착하면 수신에 성공하는 것을 검증했다.

## D05. Keep-Alive 연결의 재사용과 제한

**LMS 근거:** Connection 헤더와 Keep-Alive의 의미·처리를 이해하고 연결 수명을 관리해야 한다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 응답 하나마다 연결 종료 | 수명과 자원 관리가 단순함 | 다음 요청마다 새 연결이 필요함 |
| 같은 연결에서 여러 요청 처리 | 연결 생성 비용을 줄일 수 있음 | 다음 요청의 바이트 보존과 유휴 연결 관리가 필요하며, 스레드 풀에서는 워커를 오래 점유할 수 있음 |

- **미정:** Keep-Alive 도입 시점, 다음 요청 대기 시간, 연결당 최대 요청 수.
- **추천:** 초기에는 단일 요청·응답을 완성하고, 연결 관리 단계에서 제한을 둔 Keep-Alive를 추가한다.
- **결정 시점:** 첫 HTTP 응답 구현 시 임시 연결 정책을 명시하고, 연결 재사용 구현 전에 최종 정책을 정한다.
- **검증:** 같은 연결의 연속 요청, 다음 요청을 보내지 않는 연결, 여러 연결이 Keep-Alive로 대기할 때 새 요청의 처리를 확인한다.

## D06. 종료 시 진행 중인 연결 처리

**LMS 근거:** SIGINT·SIGTERM의 안전한 셧다운과 자원 회수를 요구한다. 진행 중인 요청을 얼마 동안 기다릴지는 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 모든 연결 즉시 종료 | 종료 시간이 짧음 | 진행 중인 요청과 응답이 끊김 |
| 모든 작업이 끝날 때까지 대기 | 진행 중인 요청을 완료할 기회를 줌 | 느리거나 멈춘 연결 때문에 종료가 지연될 수 있음 |
| 제한 시간 동안 기다린 뒤 종료 | 요청 완료 기회를 주면서 종료 시간을 제한함 | 대기 중인 작업과 처리 중인 연결을 추적해야 함 |

- **확정:** SIGINT·SIGTERM으로 종료 명령을 받으면 새 연결 수락을 중단하고, 작업 큐의 연결과 워커가 처리 중인 연결을 모두 즉시 종료한다. 요청·응답을 끝낼 시간을 별도로 주지 않는다.
- **선택 이유:** 사용자는 종료 명령을 내렸다면 진행 중인 요청의 완료를 기다리기보다 서버를 바로 끄는 동작을 원한다. 응답이 전송 도중 끊길 수 있음을 감수한다.
- **자원 정리:** 소켓 I/O 대기를 깨우고, 큐와 워커가 소유한 연결·파일·요청 메모리를 안전하게 정리하며 워커를 종료·회수한다. 즉시 종료는 요청 완료를 기다리지 않는 정책이며, 자원 정리 절차는 수행한다.
- **현재 구현:** 워커는 SIGINT·SIGTERM을 차단하고 메인이 종료 신호를 처리한다. 핸들러는 종료 표시와 논블로킹 파이프 알림만 수행한다. 메인은 새 접속을 중단하고 큐를 비운 뒤, mutex로 보호된 활성 소켓에 shutdown을 호출해 I/O 대기를 깨운다. 각 워커는 요청·파일을 정리하고 자신의 소켓을 닫으며, 메인이 모든 워커를 join한 뒤 공유 문서 루트를 닫는다.
- **결정 시점:** 스레드 풀 종료 로직 구현 전.
- **검증:** 요청 처리 중 SIGINT·SIGTERM을 보내 종료 시간, 클라이언트 결과, 워커와 소켓 정리를 확인한다.
- **검증 결과:** 빈 큐·수신 중·느린 수신자에게 송신 중·큐 포화 상태의 종료와 같은 포트 재실행을 확인했다. ASan·UBSan으로 전체 TCP 통합 테스트와 스레드 풀 단위 테스트를 통과했다. 요청 완료를 기다리는 유예 시간은 두지 않는다.

## D07. POST 본문 보관 방식

**LMS 근거:** POST 본문 처리, 매우 큰 본문에 대한 대응, 버퍼와 메모리 관리를 요구한다. 본문을 모아서 처리할지 스트리밍할지는 지정하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 본문 전체 수신 후 처리 | 파싱·라우팅·프록시로 전달하는 흐름이 단순함 | 동시 요청 수와 본문 크기에 비례해 메모리를 사용함 |
| 받으면서 처리·전달 | 큰 본문을 제한된 버퍼로 처리할 수 있음 | 수신·처리를 연결하고 중간 실패를 처리하는 로직이 복잡해짐 |

- **확정:** 본문 크기에 상한을 두고, 전체를 받은 뒤 처리한다. 사용자에게 제시한 추천을 채택했다.
- **메모리 할당:** Content-Length의 형식과 범위를 확인하고, 본문 상한 이내인지 검증한 다음 할당한다.
- **적용 범위:** 클라이언트 요청 본문을 전부 받은 뒤 처리한다는 결정이다. 응답 본문도 전부 메모리에 모아야 한다는 뜻은 아니다.
- **메모리 수명:** 요청마다 필요한 본문 저장 공간을 확보하고, 처리가 끝나거나 중간에 실패하면 해제한다. 계속 재사용하는 버퍼를 기본 크기로 축소하는 방식은 사용하지 않는다.
- **현재 구현:** 본문 크기 상한의 초기값은 1MiB다. 상한을 넘으면 메모리를 할당하기 전에 413으로 거절한다. 이 수치는 부하 테스트로 튜닝한 확정값은 아니다.
- **구현 단계:** HTTP 수신·파싱에 적용했다. 헤더는 최대 16KiB, URI는 최대 2KiB, 헤더 개수는 최대 100개로 제한하는 초기값을 사용한다.
- **검증:** 본문 분할 수신, 상한 경계와 초과, 수신 도중 연결 종료 시 메모리 회수를 확인한다.
- **검증 결과:** 11바이트 분할 본문, NUL이 포함된 본문, 1MiB 본문의 실제 TCP 수신, 길이가 부족한 본문의 EOF·무응답 처리를 확인했다. AddressSanitizer·UndefinedBehaviorSanitizer 테스트도 통과했다.

## D08. 요청 본문 길이 결정 방식의 지원 범위

**LMS 근거:** Content-Length 기반 본문 길이 처리를 명시한다. chunked 요청 본문 수신은 필수 최소 범위로 명시하지 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| Content-Length 기반부터 지원 | LMS의 최소 구현 범위에 집중할 수 있음 | 지원하지 않는 전송 방식은 명확히 거절해야 함 |
| chunked 요청 본문까지 지원 | 더 다양한 클라이언트 요청을 처리함 | 조각별 길이와 종료 경계의 파싱·검증이 추가됨 |

- **확정:** Content-Length 기반 수신부터 지원한다. chunked 요청 본문은 이번 구현 범위에서 제외한다. 사용자에게 제시한 추천을 채택했다.
- **확정:** POST에 Content-Length가 없으면 `411 Length Required`로 거절한다. 본문이 빈 POST는 `Content-Length: 0`을 요구한다. 사용자가 길이 없는 본문 요청의 거절 정책을 채택했다.
- **본문 없는 요청:** 일반 GET처럼 Content-Length와 Transfer-Encoding이 모두 없는 요청은 본문 길이 0으로 처리한다. 모든 요청에 Content-Length를 요구하는 정책은 아니다.
- **필수 처리:** 지원하지 않는 Transfer-Encoding을 무시하거나 Content-Length로 대신 해석하지 않고 거절한다.
- **현재 구현:** GET·POST와 HTTP/1.0·1.1 요청 라인, 헤더, 본문 길이를 해석한다. HTTP/1.1의 Host 누락·중복, Content-Length의 잘못된 형식·중복·범위 초과를 거절한다.
- **현재 구현:** Transfer-Encoding만 있으면 501, Content-Length와 함께 있으면 400으로 거절한다. 아직 지원하지 않는 Expect 요청은 417로 거절해 본문을 기다리는 상태에 빠지지 않게 한다.
- **구현 단계:** HTTP 수신·파싱에 적용했다. 백엔드 응답 중계 방식은 이 결정과 별도로 정한다.
- **검증:** 정상·잘못된 Content-Length, 길이 없는 POST의 411 응답, 길이 0인 POST와 길이 헤더 없는 GET의 허용, 지원하지 않는 전송 방식과 서로 충돌하는 길이 정보의 거절을 확인한다.

## D09. 정적 파일 제공 주체와 문서 루트 경계

**LMS 근거:** 문서 루트의 파일 제공, MIME과 기본 오류 응답이 필수다. Reverse Proxy 항목에서는 정적 요청을 직접 처리할지 애플리케이션 서버로 전달할지 선택할 수 있다.

- **확정:** 사용자가 나머지 추천을 채택해 C 서버가 직접 파일을 제공한다. 파일 전송을 위해 별도 애플리케이션 서버를 띄우지 않는다.
- **트레이드오프:** 파일 I/O·MIME·경로 보안을 직접 작성하지만 요구사항을 C 코드와 테스트에서 확인할 수 있다.
- **기본 구현 정책:** 문서 루트 디렉터리를 열어 유지하고 `openat()`으로 구성요소마다 접근한다. `..`와 심볼릭 링크를 거절하고 일반 파일만 제공한다. 디렉터리 목록은 제공하지 않는다.
- **현재 구현:** 정상 파일은 200, 없음은 404, 권한·금지된 경로는 403, 예상하지 못한 파일 오류는 500으로 응답한다.
- **검증:** 직접·인코딩된 경로 우회, 루트 안/밖을 가리키는 링크, 디렉터리 링크, FIFO와 권한 거절을 확인했다. 500 응답은 유효하지 않은 루트 디스크립터를 주입한 모듈 테스트로 확인했다.

## D10. 정적 파일 전송 방식

**LMS 근거:** 파일 내용을 HTTP 응답 본문으로 전송해야 하며 메모리·자원 관리와 macOS/Linux 이식성을 고려한다. read/send 사용을 직접 지정하지는 않는다.

| 선택 | 장점 | 비용·제약 |
| --- | --- | --- |
| 전체 파일을 읽은 뒤 전송 | 흐름이 단순함 | 파일 크기와 동시 요청 수만큼 메모리 사용 증가 |
| read/send 반복 | 일정 크기의 작업 공간으로 큰 파일 전송 가능, 공통 API 사용 | 읽기와 송신의 진행·오류를 관리해야 함 |
| sendfile | 사용자 공간으로의 데이터 복사를 줄일 수 있음 | POSIX 표준 함수가 아니며 OS별 호출 방식 차이와 LMS의 표준 범위를 고려해야 함 |

- **확정:** 사용자가 read/send를 선택했다. 파일 전체를 메모리에 적재하지 않고 나눠 읽어 전송한다.
- **현재 구현:** 16KiB 작업 공간을 반복 사용한다. `fstat()`으로 얻은 파일 크기를 Content-Length로 쓰고 읽은 바이트를 전부 송신한 뒤 다음 블록을 읽는다.
- **오류 처리:** 첫 읽기 실패는 200 전송 전에 500으로 처리한다. 응답 시작 후 파일이 줄거나 송신이 실패하면 연결을 닫는다. 이미 보낸 응답에 500을 덧붙이지 않는다.
- **검증:** 빈 파일, NUL이 포함된 다중 블록 바이너리, 실제 TCP의 4MiB 파일과 수신 중 클라이언트 종료를 확인했다.

## D11. 실행 설정 입력 방식

**LMS 근거:** 포트·문서 루트·프록시 설정은 CLI 또는 설정 파일로 받는다.

- **확정:** 사용자가 추천을 채택해 CLI를 사용한다. 설정 파일 파싱은 이번 단계에 추가하지 않는다.
- **트레이드오프:** 실행 인자로 쉽게 재현할 수 있지만 설정이 많아지면 명령이 길어진다.
- **현재 구현:** `--port`/`-p`, `--root`/`-r`, `--help`/`-h`와 긴 옵션의 `=` 형식을 지원한다. 기본값은 8080과 `./www`다. 0은 OS 포트 할당을 사용한다.
- **검증:** 기본값, 옵션 형식, 잘못된 포트·누락 값·없는 루트·파일을 루트로 지정한 경우와 실제 선택한 포트·루트의 동작을 확인했다.
- **이후 작업:** 백엔드와 프록시 라우팅 설정은 6단계에서 CLI에 추가한다.

## D12. 정적 요청과 API 요청의 경로 분리

**LMS 근거:** Reverse Proxy는 경로나 Host 기반으로 라우팅할 수 있다.

- **확정:** 사용자가 경로 기반 추천을 채택했다. `/api`와 `/api/*`는 애플리케이션 서버로 전달할 영역으로 예약하고 그 외는 정적 파일로 처리한다.
- **트레이드오프:** 한 사이트에서 구분하기 쉽지만 이 경로 영역에는 정적 파일을 제공하지 않는다.
- **현재 구현:** `/`와 `/docs/`는 `index.html`을 찾는다. 정적 파일은 GET만 허용하며 POST에는 405와 `Allow: GET`을 보낸다. API 영역은 프록시 구현 전까지 501로 응답한다.
- **경로 처리:** 쿼리 분리 → 한 번의 퍼센트 디코딩 → 경로 검증·정규화 → 라우팅 순서다. 실제 프록시 전달 시 원래 요청 주소는 그대로 사용할 수 있도록 남겨 둔다.
- **검증:** 루트·중첩 index, 쿼리, 공백·한글 파일명, `/api`와 `/apix` 경계, 잘못된 인코딩과 상위 경로의 거절을 확인했다.

## 결정 확정 시 기록할 내용

- 선택한 정책과 이유
- 선택하지 않은 대안의 비용
- 적용할 제한값과 그 값의 근거
- 구현 여부와 검증 결과

LMS의 필수 동작은 유지한다. 위 추천과 임시 구현값을 확정된 결정으로 간주하지 않는다.
